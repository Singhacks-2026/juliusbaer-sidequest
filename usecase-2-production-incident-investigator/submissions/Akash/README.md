# Incident Clarity

**An evidence-first investigation assistant for on-call engineers.** It connects the symptom, logs, deployment changes, known issues and runbooks into one reviewable incident report. When evidence is insufficient, it explains the gap instead of inventing a diagnosis.

This separate project implements [Use Case 2 — Production Incident Investigator](https://github.com/MrAkashKumar/juliusbaer-sidequest/tree/main/usecase-2-production-incident-investigator). It contains exactly the three submission files requested by that repository:

| File | Purpose |
|---|---|
| `solution.py` | Working `investigate(query: str, corpus: dict) -> dict`, ingestion, TF-IDF retrieval, correlation, confidence and CLI |
| `answers.json` | Reports actually generated by this implementation for both supplied incidents |
| `README.md` | Problem, priorities, architecture, guardrails, impact model, design and verification |

The existing Payment Clarity project is separate. No API key is copied or used: this track explicitly permits a solution without an LLM. No upstream source files are modified, no production integration is connected, and nothing is submitted to GitHub automatically.

## The specific problem

An on-call engineer must decide which noisy signals explain an incident, which change is relevant, and whether a runbook applies. A keyword search can rank an architecture document highly without identifying the cause. A same-component warning can still be unrelated. A fluent explanation can turn an uncertain diagnosis into a dangerous remediation recommendation.

This repo supplies synthetic operational scenarios, not evidence about Julius Baer's actual manual processes, staffing, incident volumes, customers or recovery performance. The problem we address is the investigation work represented by those scenarios; any claim about current bank practices needs validation with its operations team.

**Priority:** shorten the time to a defensible investigation and safe next step. Automatic recovery is outside scope.

## Two concrete use cases

### A. Payment failures after a configuration deployment

- At **14:30 UTC on 2 September 2026**, adapter release **v2.4.1** reduced its connection pool from **50 to 10**.
- The first supplied matching error is at **14:47:12**, a **17 minute 12 second** gap. Temporal proximity supports correlation; it is not proof by itself.
- Logs show `ConnectionPoolTimeoutException` in `payment-gateway-adapter` and `GATEWAY_TIMEOUT` in `payment-service`. Successes between failures establish an intermittent symptom, rather than a complete outage.
- CSV issue **KI-101**, runbook **RB-014**, and precedent **INC-2031** independently support the undersized-pool hypothesis.
- Directly impacted components: **payment-gateway-adapter** and **payment-service**. Unrelated search, checkout, email formatting, auth, refund and database entries do not establish additional impact.
- The proposed action is to validate utilization/current configuration, then have an authorised operator restore the prior baseline or appropriately size the pool and redeploy. Verify recovery after the change.
- **Generated score: 90/100. Runbook estimate: 20 minutes.** The prior incident took 22 minutes. Neither value is measured recovery for this current incident; the supplied logs contain no recovery completion event.

There are five explicit failed charge records in the excerpt. That is a sample count, not five unique affected customers, a complete failure count, or a failure rate.

### B. Delayed order confirmation emails with uncertain cause

- `notification-service` queues and eventually sends all four shown emails; payment and order operations succeed in the supplied window.
- Exact queued-to-sent durations are **46m35s, 42m26s, 75m24s and 56m43s**. These are observed email latencies, not MTTR or a measured SLA violation: the API document contains no delivery SLA.
- One warning reports **340 queued messages**. This is a queue snapshot, not a customer count or proof that worker capacity caused the delays.
- Payment-component deployments occur after this incident and do not affect the notification component. They cannot explain its onset.
- There is no matching confirmed known issue or precedent. The email-formatting issue does not explain delivery latency.
- The notification runbook lacks the required metrics and explicitly says its **15-minute** estimate may not apply. The implementation therefore returns **`mttr_minutes: null`**.
- **Generated score: 20/100; human review required.** Collect queue age, consumer/concurrency metrics, provider latency and correlated per-stage traces. Do not blindly scale consumers.

The useful outcome here is a precise evidence request and a bounded hypothesis, even when the root cause remains unknown.

## Users and measurable value

| User | Current investigation burden represented by this use case | Product benefit |
|---|---|---|
| On-call engineer | Manually cross-reference logs, changes and runbooks | One report with exact supporting excerpts and missing evidence |
| Incident commander | Reconstruct the diagnosis and scope from scattered messages | Clear affected components, uncertainty and proposed next step |
| Service owner | Check whether a proposed fix fits the actual change | Inspect the source change and matching signature before authorising remediation |
| Relationship manager / customer support | Request technical updates and translate them for customers | Future reviewed status summary; this submission does not generate or send customer notices |
| Customer | Experience a failing charge or delayed confirmation | Potentially faster service restoration and clearer updates; not yet measured |

An RM is an indirect beneficiary, not the operator of this tool. Technical incident details should first go to the incident owner; any customer communication must be reviewed and limited to confirmed service impact.

### Impact model — assumptions, not observed bank results

Example pilot: **24 incidents/month × 2 investigators × (45−15) minutes = 24 engineer-hours/month saved**, or 288 hours/year if the volume and improvement persist. The assumed per-person investigation time reduction is 67%. This does not mean end-to-end MTTR falls 67%: deployment, approvals and recovery verification may dominate that time.

For an illustrative pilot team of six engineers and two coordinators, eight direct users could benefit. Actual bank user/customer reach is unknown. Measure affected unique customers from authorised transaction/telemetry joins; do not infer them from service count, queue depth or the tiny supplied log sample.

Pilot measurement: compare matched historical cases with and without the tool; record time to first evidence-backed diagnosis, evidence completeness, incorrect high-confidence diagnoses, time spent reviewing, and time to recovery separately. Have service owners adjudicate correctness. The two supplied incidents are acceptance examples, not an accuracy benchmark.

## Architecture and technology

```text
Caller / CLI
  → validate query and corpus
  → ingest prose sections + individual CSV rows
  → TF-IDF cosine retrieval
  → select symptom-relevant log component / error signature
  → retrieve again with component + signature
  → correlate independent evidence categories
  → extract scoped remediation and applicable runbook estimate
  → calculate confidence and review flag
  → exact seven-field report → answers.json
```

**Implemented stack:** Python 3.10+ standard library (`csv`, `re`, `collections`, `math`, `datetime`, `json`, `pathlib`). No pip packages, vector database, GPU, API costs or background service. The corpus already fits in memory; introducing infrastructure would add setup without solving the evidence-correlation problem.

TF-IDF determines retrieval order. Correlation then checks eligibility; the highest-ranked document alone cannot establish a cause. Markdown sections and CSV rows retain their original source names and text. Evidence is not fabricated from a summary. Filenames and incident IDs are not used to select a canned answer.

**Future integration boundary:** adapters should produce the same `filename → text` corpus with separate incident IDs, source timestamps, hashes and access metadata maintained outside the seven-field competition report. A future FastAPI wrapper can accept an incident reference and call the same core. A React/TypeScript UI can render structured results. Read-only connectors for observability, deployment history and issue tracking are proposed, not implemented or guaranteed compatible with every system. Each needs its own authentication, mapping, freshness and access controls.

An optional LLM could later paraphrase an already verified report. It must not compute the confidence, extend the blast radius, manufacture citations, decide a rollback or replace a missing MTTR. It is unnecessary for this deliverable.

## Confidence and guardrails

The score is an **explainable heuristic**, not a statistically calibrated probability:

| Corroborating category | Points |
|---|---:|
| Relevant exception in application logs | 20 |
| Same-component known-issue signature | 25 |
| Related configuration deployment before symptoms | 25 |
| Matching runbook | 10 |
| Matching historical incident | 10 |

Repeated lines or duplicate documents do not add category points. Without a known-issue match, the exception route is capped at 45. Thin symptom-only evidence receives 20; no relevant log evidence receives 0. A receives 90 because all five categories match. B has observed symptoms but no supported causal chain, so receives 20.

1. **Human authority:** the challenge requires `needs_human_review: false` at scores of 50 or above. This only means the report is not flagged by that threshold. Every production mutation still requires an authorised human; the code exposes no mutation tools.
2. **Temporal scope:** exclude deployments after the first matching error and require the same component plus configuration-term overlap. This is a heuristic correlation filter, not causal proof.
3. **Impact scope:** report observed component impact; include an upstream error only when the supplied architecture/API supports the relationship. Do not automatically label the external provider or the entire bank as impacted.
4. **MTTR provenance:** extract an applicable runbook typical estimate only for a sufficiently supported hypothesis. Unconfirmed/non-applicable estimates remain null; observed delays and historical recovery are not substitutes.
5. **Source integrity:** citations use original filenames and exact excerpts. In the future, add version hashes and source-age warnings; current files are static inputs.
6. **Untrusted input:** corpus text is parsed as data. No `eval`, shell commands, network calls or interpretation of document instructions. Input format is validated. Production ingestion also needs size limits and sensitive-data filtering.
7. **Secrets and privacy:** this project does not read the Payment Clarity `.env`, load credentials or transmit logs externally. Real logs may contain identifiers and require access controls and redaction before ingestion.
8. **Conflicts:** competing strong error hypotheses and semantic contradictions are not fully adjudicated by this prototype; route them to human review in a production wrapper. The API/architecture retry wording differs in incident A, so this implementation does not infer a retry-storm root cause or recommend automatic retries.

## Run and reproduce

From this project directory, with a local checkout of the linked repository:

```bash
python3 -B solution.py \
  --data-dir /path/to/juliusbaer-sidequest/usecase-2-production-incident-investigator/data \
  --output answers.json
```

Replace `/path/to/juliusbaer-sidequest` with your checkout path. No upstream code needs modification. The program discovers incident folders containing `query.txt`; it loads each folder's `.md` and `.csv` files. You can also import `investigate` and supply an in-memory corpus directly.

The included answers were generated from a public repository snapshot downloaded on **5 September 2026**. The snapshot is not pinned to an upstream commit, and future upstream edits may change outputs. For submission, copy these three files into the repo's `usecase-2-production-incident-investigator/submissions/<your-name>/` directory, then regenerate against that checkout. No private grading key was accessed or run.

## Verification and limitations

Executed checks passed for both expected cases; exact output keys and types; confidence/review consistency; every citation's source membership; expected A impact and 20-minute estimate; B's null MTTR; corpus-order invariance; renamed source files; missing deployment; empty corpus; duplicated logs; and rejection of a future deployment as corroboration.

The implementation deliberately supports the supplied log/table/document conventions. Other log schemas, languages, cause types, multiple concurrent faults, stale historical analogies or conflicting evidence require additional parsers and evaluation. Source headings identify document categories; renamed files work, but arbitrary rewritten headings are not guaranteed. Matching sources are independent categories, not proof that their authors or underlying information are independent. Confidence weights need validation on a broader incident set before production use.

The core does not require an LLM to deliver the important behaviour: showing why incident A is well-supported and why incident B is not. No alternative model experiment or production benchmark is claimed.
