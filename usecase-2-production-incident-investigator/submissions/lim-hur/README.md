## Understanding of the problem

The difficult part is preserving the distinction between symptom, mechanism, trigger, and recovery estimate.
A document can mention the right service while describing an entirely different operation, such as refund webhooks versus charge processing.
A retrieved runbook can contain an attractive number that is explicitly inapplicable.
An architecture diagram describes dependencies, not proof that every depicted system is impaired.
The solution therefore retrieves candidate evidence and then applies explicit correlation gates before forming a causal claim.

## Design

1. **Ingest without losing provenance.** Content identifies document roles; filenames are retained only as citation labels.
   CSV records are parsed with `csv.DictReader`, including quoted commas and multiline cells.
   Logs become timestamped events, deployment rows become structured changes, architecture bullets become component descriptions, and runbook/history/API sections stay intact.
   Keeping sections intact preserves qualifiers attached to recommendations and MTTR.
   Every emitted excerpt is checked as an exact substring of the supplied source.
2. **Retrieve in two passes.** BM25 ranks passages using term-frequency saturation and length normalization (`k1=1.5`, `b=0.75`, positive smoothed IDF).
   A small, explicit lexical normalization map handles inflections and vocabulary such as payments/charges and late/delayed.
   The query's symptom subject scopes candidate components.
   A runtime exception matching a catalog signature expands retrieval to that component and mechanism, which brings in relevant runbooks and historical records even when the initial query lacks their terminology.
3. **Correlate, rather than count hits.** Candidate causes require a query-relevant component and an affirmative runtime signature.
   The latest preceding deployment for that component must also overlap the mechanism; future or directionally conflicting changes suppress confidence.
   Runbooks and historical cases must match both the component and exception, and unconfirmed material cannot supply a recovery estimate.
   Simultaneous downstream errors require a documented dependency, so unrelated same-time errors do not enlarge the impact list.
4. **Abstain explicitly.** When there is no supported catalog mechanism, the result states that the cause is unknown.
   Correlated queue/send measurements can establish the symptom, while consumer or provider explanations remain hypotheses.
   Missing instrumentation and conflicting or inapplicable references are cited without treating them as positive causal evidence.
5. **Render deterministically.** Service names, release versions, configuration values, timestamps, delays, source excerpts, and MTTR come from input data.
   The seven output keys match the required contract, and `needs_human_review` is derived from the final score exactly.

## Confidence rubric

The score is a transparent evidence-strength rubric, not a statistically calibrated probability of correctness.
Two supplied incidents cannot justify a fitted probabilistic calibration model.

| Corroboration channel | Maximum contribution |
|---|---:|
| Affirmative runtime signature | 25, or 15 for a single event |
| Matching catalog mechanism | 25 |
| Component, mechanism, and time-aligned deployment | 20 |
| Matching earlier incident | 12 |
| Matching, qualified runbook | 10 |
| Architectural consistency | 3 |

Repeated events do not add points beyond their channel's limit.
Identical documents and log events are deduplicated, duplicate catalog rows do not create competing hypotheses, and a source file receives at most one vote across the main causal channels.
Fewer than three distinct causal source files, or the absence of both deployment and historical corroboration, caps the score at 49.
Conflicting changes or closely competing hypotheses cap it at 40; the overall maximum is 95.
The ambiguous delay path scores 25 for the measured symptom and 30 when a queue warning supplies a tentative lead, remaining below the review threshold.
These source roles are corroboration channels, not a claim that the underlying documents are statistically independent.
A production calibration study would need more labeled incidents, held-out evaluation, and reliability diagrams before interpreting scores as probabilities.

## Approach and tradeoffs

Whole-document retrieval was insufficient because unrelated entries share vocabulary and can dominate the ranking.
The implementation uses passages and explicit source-role selection so an architecture hit cannot displace a relevant catalog row or runbook.
An early architecture parser grouped adjacent bullets together; a renamed-component regression exposed the resulting attribution error, and ingestion now separates those descriptions.
Additional adversarial checks exposed duplicate catalog hypotheses and negated exception mentions; the final version deduplicates equivalent anchors and rejects simple explicit negations.

BM25 was chosen over TF-IDF because length normalization and term-frequency saturation are useful for this mixture of short log entries and longer procedural sections.
Both are viable for this small corpus; the correlation logic matters more than the retrieval formula.
Embedding models, a vector database, and an LLM were considered unnecessary here because the decisive links are exact runtime identifiers, component ownership, dates, and explicit qualifiers.
Avoiding them keeps execution reproducible, removes network and model-version dependencies, and prevents unsupported prose from filling evidence gaps.
The runtime exception index avoids rescanning every log for every catalog candidate.
The whole corpus is small enough to inspect every candidate within each required source role instead of imposing a lossy global top-k cutoff.

There are deliberate limits.
This is a conservative investigator for the supplied English document schemas, not a universal natural-language causal reasoner.
Novel mechanisms without recognizable exception signatures fall back to uncertainty and evidence gathering.
The lexical map, heading/field recognizers, and simple negation rules will need expansion for different operational formats or languages.
Queue pairing uses available correlation IDs and cannot resolve multiple concurrent message instances that share only an order ID; production telemetry should use unique message IDs and trace/span context.
No success event is treated as proof that the entire incident recovered.
Actual incident MTTR remains unmeasurable without a confirmed recovery event, even when the report provides a runbook-based estimate.

## Reproduce and verify

From the repository root:

```bash
python3 usecase-2-production-incident-investigator/submissions/lim-hur/solution.py
python3 usecase-2-production-incident-investigator/submissions/lim-hur/solution.py --self-test
```

The first command regenerates `answers.json` from the two incident directories.
`--data-dir` and `--output` allow an explicit input directory and output location.
The self-test is embedded in `solution.py` to keep the submission to the three requested files; fixture-specific expectations are confined to that test function.

Validation passed 358 checks across schema/provenance validation, both official incidents, deterministic reruns, shuffled input, renamed files/components, empty and invalid input, evidence ablations, duplicated documents/logs/catalog rows, negated exceptions, future and conflicting deployments, changed configuration/MTTR values, missing correlation IDs, simultaneous unrelated errors, query paraphrases, and multiline CSV ingestion.
The checks include complete report generation and JSON serialization, not just isolated helper assertions.
The embedded benchmark completed 100 investigations in approximately 0.20 seconds on the development machine, about 2ms per report; this is a local measurement, not a throughput guarantee.
Ruff lint and formatting checks pass.

```bash
uvx ruff check usecase-2-production-incident-investigator/submissions/lim-hur/solution.py
uvx ruff format --check usecase-2-production-incident-investigator/submissions/lim-hur/solution.py
```

Development used Python 3.14.4 and Ruff 0.16.6.
The implementation uses Python 3.10-compatible syntax and standard-library APIs; the stated minimum is not a claim that every Python release was tested.
The official loader was used separately to verify that its reports exactly match the submitted JSON.
No browser interface is part of this challenge; the end-to-end interface is the official corpus, `investigate()`, and the generated artifact.

## Research informing the design

- [Stanford Introduction to Information Retrieval: BM25](https://nlp.stanford.edu/IR-book/html/htmledition/okapi-bm25-a-non-binary-model-1.html) explains term-frequency saturation, length normalization, and reasonable untuned parameters.
- [Google SRE: Effective Troubleshooting](https://sre.google/sre-book/effective-troubleshooting/) motivates hypothesis testing with confirming and disconfirming observations and avoiding spurious correlations.
- [OpenTelemetry logging specification](https://opentelemetry.io/docs/specs/otel/logs/) motivates correlating operational events using timestamps, execution context, and trace/span IDs.

These references inform the method and proposed instrumentation only.
All incident findings and citations are derived exclusively from the challenge corpus.
AI assistance was used for research, implementation, review, and regression-test development.
